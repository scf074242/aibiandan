# LLM 自动编排技术方案书修订稿（可直接替换原文档相关章节）

## 1. LLM 总体设计

本系统中的 LLM 定位为“编排代理”，不直接替代编排老师完成完整节目单写表，而是在系统约束下承担以下职责：

1. 理解用户自然语言意图，识别当前任务属于完整生成、局部补排、局部微调、仅校验或仅修复等模式。  
2. 基于当前待编排空窗、频道上下文、版面参考、历史编排参考、候选节目集合等信息，生成结构化命令。  
3. 在系统检索返回的候选节目集合中做选择，并给出简要解释。  
4. 在校验失败时，根据结构化校验报告选择修复策略。  

LLM 不负责以下工作：

- 不直接生成完整业务落表对象  
- 不直接决定精确时间边界  
- 不直接做全表合法性判断  
- 不直接写入业务数据  
- 不直接控制长程任务的循环、回退与终止

所有对串联单的写入必须通过原子能力层执行，所有写入结果必须经过系统校验层确认。这样可以确保大模型只参与“理解、筛选、选择和解释”，而精确执行、规则判定和状态控制仍由确定性系统完成。

## 2. 核心设计原则

### 2.1 可信业务数据决定边界
编排过程中的时间边界、固定时段和不可变约束，必须优先来自可信业务数据，包括但不限于：

- 播出版面
- 昨日及近几日编排单
- 固定播出项
- 直播占位
- 广告规则
- 人工锁定项
- 频道播出配置

LLM 不参与主观设定节目块的起止边界，只在这些已知约束之内进行策略选择和候选判断。

### 2.2 以空窗为核心驱动编排
系统通过 `queryRemainingGaps()` 或等价接口持续返回当前待编排空窗列表。  
初始状态下，可以是全天空窗，也可以是版面、固定项和锁定项切分后的若干空窗；随着节目逐条写入，空窗会不断被切分、缩小和消除。系统每一轮只处理一个当前空窗，直到空窗清零或剩余问题转人工处理。

### 2.3 LLM 只在“局部上下文”中工作
LLM 每次只面向当前空窗及其必要上下文工作，输入内容控制为：

- 当前空窗信息
- 前后邻条目摘要
- 当前频道和日期
- 版面参考摘要
- 昨日或近几日参考摘要
- 当前已用节目摘要
- 候选节目集合
- 当前校验摘要

这样可以降低长上下文漂移风险，并使每轮决策更稳定、更容易调试和复盘。

### 2.4 系统托管长程任务
完整编排属于长程任务，不能依赖 LLM 在单轮对话中持续自发执行。系统必须通过编排控制器维护任务状态、空窗列表、执行进度、回退点和校验结果。LLM 每一轮只完成当前步骤的局部决策。

## 3. 主流程设计

### 3.1 入口：统一任务判别
无论用户是点击“AI 智能编排”入口，还是通过对话面板提出自然语言请求，系统都先经过“任务判别器”判断当前任务类型。任务判别综合三类信息：

1. 当前节目单状态  
   - 是否为空表  
   - 是否已有已选中时间段  
   - 当前空窗分布情况  
2. 用户语义  
   - 是否表达从零生成、补排某段、替换某条、删除某条、校验、修复等意图  
3. 风险等级  
   - 是否影响长时间段  
   - 是否属于批量调整  
   - 是否涉及高风险命令  

最终统一归类为以下模式之一：

- `full_generate`：从零生成完整编排单  
- `partial_generate`：对当前一个或多个空窗自动补排  
- `micro_edit`：局部增删改查  
- `validate_only`：只执行校验  
- `repair_only`：只执行修复  
- `clarify`：语义不明确，需先澄清

### 3.2 完整编排主链路
当任务被识别为完整生成或局部补排时，系统执行如下链路：

1. 创建 `planning_session`，保存频道、日期、目标、参考优先级、用户偏好和任务状态。  
2. 拉取频道信息、播出版面、历史编排、节目库、收视率、固定播出项和锁定项。  
3. 调用 `queryRemainingGaps()` 获取当前待编排空窗列表。  
4. LLM 输出一次“编排策略初始化”，只描述编排原则和优先级，不输出完整节目单。  
5. 主循环开始：  
   - 选择一个当前空窗  
   - LLM 输出 `QueryCandidatesCommand`  
   - 系统调用候选检索接口，返回 `ProgramCandidate[]`  
   - LLM 输出 `FillItemCommand`，只选择当前最合适的候选节目  
   - 系统将选中节目物化为现有业务数据对象  
   - 调用原子能力执行写入  
   - 自动触发校验  
   - 重新计算空窗列表  
6. 当空窗清零后，执行全量校验；如仍存在可修复问题，则进入有限轮次修补；仍无法修复的，转人工处理。

### 3.3 单轮填充的最小执行节奏
在线主流程应统一采用以下最小节奏：

- 单空窗  
- 单次候选检索  
- 单条候选选择  
- 单次物化写入  
- 单次自动校验  

这样可以保证每一步都可解释、可回退、可中止，适合真实业务环境下的逐步编排。

## 4. 长程任务实现机制

### 4.1 长程任务的本质
“从零生成某天某频道完整编排单”是一个典型长程任务，通常需要处理几十到上百次局部决策，不适合让 LLM 以“一次性输出完整结果”的方式完成。长程任务的可实现性来自于：

- 任务状态持久化  
- 空窗驱动  
- 单轮局部决策  
- 自动校验  
- 局部回退  
- 有限轮次修补  

### 4.2 编排控制器职责
编排控制器负责：

- 创建和维护 `planning_session`
- 保存当前节目单状态
- 维护空窗队列
- 选择当前处理空窗
- 控制 LLM 调用顺序
- 控制重试、回退、降级和终止
- 记录校验结果和执行日志

LLM 不负责管理上述状态，也不负责自己决定是否继续循环、是否回退或是否结束任务。

### 4.3 长程任务推荐执行链路
以“从零生成明天某频道全天编排单”为例，控制器执行过程如下：

1. 初始化会话  
2. 获取可信业务数据  
3. 获取初始空窗  
4. 生成策略初始化  
5. 循环处理空窗  
6. 每轮写入后自动校验  
7. 更新空窗  
8. 空窗清零后执行最终校验  
9. 修补或人工接管  

整个过程不是由 LLM 自主连续思考完成，而是由系统在多轮局部决策中逐步构造完整编排单。

### 4.4 长程任务的终止条件
满足以下任一条件即可终止自动编排流程：

- 当前空窗列表为空，且校验通过  
- 剩余问题均已进入人工确认队列  
- 达到修补次数上限，转人工处理  
- 用户主动停止编排

## 5. 局部微调机制

### 5.1 微调入口
局部微调通过自然语言入口或表格编辑入口触发。自然语言入口由 LLM 识别意图，转成标准命令；表格编辑入口则由系统直接转换为等价命令。

### 5.2 微调支持的命令类型
建议保留以下命令类型：

- `insert`
- `delete`
- `replace`
- `move`
- `update_field`
- `batch_update`
- `validate`
- `repair`

### 5.3 微调的统一执行链路
无论来源于自然语言还是人工编辑，微调执行链路统一为：

1. 识别命令类型与参数  
2. 生成命令预览  
3. 用户确认  
4. 调用原子能力执行  
5. 自动触发校验  
6. 若产生新空窗，则自动进入局部补排流程  
7. 若无法自动补齐，则转人工处理

### 5.4 风险分层
微调命令分为两级：

#### 安全命令
- 单条替换
- 单条删除
- 单条移动
- 单字段修改

安全命令可在预览后快速确认执行。

#### 高风险命令
- 批量替换
- 批量时间平移
- 影响长时间段的批量更新
- 可能引起大范围空窗重算的操作

高风险命令必须先做预演，展示影响范围和潜在校验风险，再由用户确认执行。

## 6. 命令体系设计

### 6.1 PlanCommand：策略初始化
`PlanCommand` 的职责调整为“编排策略初始化”，只描述：

- 编排目标
- 参考优先级
- 是否优先顺排
- 是否允许 filler
- 风险偏好
- 当前优先处理的空窗类型

`PlanCommand` 不再直接输出完整节目块列表，而是作为主流程启动时的策略说明与初始化依据。

### 6.2 QueryCandidatesCommand：候选检索条件生成
针对当前空窗，LLM 输出检索条件，包括：

- 目标时间段
- 期望时长
- 节目类型偏好
- 是否优先顺排
- 是否排除已用内容
- 是否参考收视率
- 是否允许短内容补齐

系统依据这些条件从节目库、多源参考数据和历史编排中检索候选节目。

### 6.3 FillItemCommand：单条候选选择
LLM 在候选集合中选择当前最合适的一项，只输出：

- 当前空窗标识
- 选中的候选节目
- 简要选择理由
- 是否建议后续继续顺排或补缝

LLM 不直接输出完整业务对象，不负责填充全部字段。

### 6.4 RepairCommand：修复策略选择
当校验不通过时，系统先生成结构化校验报告，并给出允许的修复动作。LLM 只在这些动作中做选择，例如：

- 替换候选
- 补短片
- 调整一条
- 局部回退
- 请求人工确认

## 7. 数据结构与物化策略

### 7.1 现有业务数据结构保持不变
本方案不要求调整现有业务数据结构。现有 `RundownItem`、`ScheduleItem`、`ProgramLibraryItem`、`GapInfo`、`ProgramCandidate` 等结构均可继续使用。

### 7.2 增加确定性物化器
为了让 LLM 输出保持轻量且可靠，系统应增加“确定性物化器”，负责将 LLM 的候选选择结果转成完整业务对象。

物化器输入：

- 当前空窗  
- LLM 选中的节目  
- 节目库明细  
- 前后邻条目摘要  
- 当前频道上下文  

物化器输出：

- 完整 `RundownItem`
- 再通过现有转换逻辑生成 `ScheduleItem`

### 7.3 由系统补齐的字段
以下字段应由系统自动补齐，而非由 LLM 自由生成：

- `broadcastTime`
- `endTime`
- `duration`
- `sequence`
- `id`
- `sortOrder`
- `deliveryStatus`
- `broadcastType` 映射字段
- 部分固定业务属性

这样可以确保大模型的输出焦点只停留在“选什么”，而不是承担业务字段拼装和精确时间推算。

## 8. 接口设计建议

在不修改现有业务数据结构的前提下，应增加面向编排代理的接口层。建议至少包括以下接口：

### 8.1 读取类接口
- `get_generation_context(channelId, date)`
- `get_program_details(programCode)`
- `query_remaining_gaps()`
- `query_candidates_by_multi_source(params)`
- `get_recent_schedule_reference(channelId, date, days)`
- `get_layout_reference(channelId, date)`

### 8.2 预演类接口
- `materialize_fill_item(params)`
- `preview_command(command)`
- `simulate_batch_command(command)`

### 8.3 执行类接口
- `execute_command(command)`
- `append_items(items)`
- `replace_item(params)`
- `delete_item(params)`
- `move_item(params)`
- `validate_schedule(scope)`
- `execute_repair_action(action)`

### 8.4 解释类接口
- `explain_candidate_selection(candidateId)`
- `summarize_validation_issues(scope)`
- `explain_command(command)`

通过这组接口，LLM 只与“编排能力层”交互，而不直接操作底层数据存储。

## 9. 校验、修补与回退机制

### 9.1 校验层是最终裁决者
所有写入完成后，系统立即执行确定性校验。校验层负责：

- 空窗检测
- 重叠检测
- 首尾边界匹配
- 成品关联检测
- 素材关联检测
- 时长一致性检测

校验层输出结构化 `ValidationReport`，供 UI 展示、修补流程和人工确认共同使用。

### 9.2 回退机制
为保证方案健壮性，建议设置三级回退：

1. **条目级回退**：当前候选不合适时，换一个候选重新写入  
2. **空窗级回退**：当前空窗连续失败时，回退该空窗内最近若干条  
3. **会话级人工接管**：多轮修补失败后，暂停自动编排，转人工处理  

### 9.3 修补机制
修补采用有限轮次执行。每轮流程为：

1. 系统生成结构化校验报告  
2. 生成允许的修复动作  
3. LLM 选择修复策略  
4. 系统执行修复  
5. 重新校验  

如达到修补上限仍无法收敛，则转人工接管。

## 10. 适用范围与扩展能力

该方案不仅适用于传统电视频道编排，也可兼容以下场景：

- 轮播单编排
- 专题编排
- 节目晚会
- 直播编排
- 其他受约束内容编排场景

不同场景的约束重点不同，但技术本质相同，均属于“在既定约束下完成内容筛选、排序、填充与校验”的问题。  
因此，底层可统一复用：

- 任务判别器
- 空窗驱动主流程
- 两阶段候选检索与选择
- 原子能力执行
- 自动校验与修补

其中，在晚会和直播场景中，AI 更适合定位为“辅助编排与快速调整工具”，承担候选推荐、时长补齐、冲突检测和校验修复等工作，在保留人工审核把关的前提下提升效率与应变能力。

## 11. OpenClaw 等通用 Agent 框架的接入定位

如后续需要接入 OpenClaw 等通用 Agent 框架，建议其定位为：

- 自然语言入口层
- 工具编排壳
- 会话承载层
- 跨渠道协同入口

核心编排、物化、写入、校验和发布仍然由平台自身服务承担。  
也就是说，OpenClaw 不替代编排引擎，只调用编排能力接口。最终确认与发布仍需回到平台 UI 中完成。

## 12. 原型开发建议

面向近期原型开发，建议按以下顺序推进：

### 第一阶段：跑通最小闭环
- 频道与日期选择
- `queryRemainingGaps()` 返回空窗
- `QueryCandidatesCommand` 与 `FillItemCommand` 串起来
- 单条物化写入
- 自动校验
- 表格高亮与空窗重算

### 第二阶段：增加完整生成能力
- 编排策略初始化
- 编排控制器
- 空窗循环处理
- 进度展示
- 有限轮次修补

### 第三阶段：增加对话微调能力
- 自然语言意图识别
- 命令预览
- 命令确认
- 命令执行
- 微调后自动补排

### 第四阶段：扩展场景与能力
- 轮播单兼容
- 晚会与直播辅助编排
- 更复杂的修补策略
- 外部 Agent 入口接入

---

## 13. 方案总结

本方案的核心不是追求“LLM 一次性自动排完整天节目单”，而是建立一套可控、可验证、可修复的自动编排体系：

- 可信业务数据决定边界  
- 系统控制主循环、回退和终止  
- LLM 只在局部上下文中做受约束决策  
- 所有写入通过原子能力执行  
- 所有结果通过确定性校验兜底  

因此，该方案既适合当前论证阶段，也具备直接落入原型开发的可操作性。后续无论继续扩展到更完整的电视编排、轮播单、晚会或直播场景，整体架构都不需要推翻，只需在同一套空窗驱动与编排控制体系上逐步增强即可。
