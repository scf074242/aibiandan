# 版面草案工作流

更新时间：2026-04-13

## 目标

这条链路解决的是“用户先描述版面，再确认是否开始编排”的场景，而不是直接修改已编排节目。

当前支持三类来源统一进入草案流程：

- 当前频道已有版面
- 用户导入的上传版面
- 根据自然语言即时生成的 AI 草案

## 整体流程

1. 用户输入全天编排、补空窗、按时段重排等需求。
2. 系统先判断这句话是不是原子命令。
3. 如果不是原子命令，再进入版面意图识别。
4. 命中版面意图后，生成或微调一份 `LayoutDraft`。
5. 草案只在右侧对话区展示，左侧表格继续保留真实节目单视图。
6. 用户继续通过自然语言微调草案。
7. 用户点击“开始编排”后，草案被注册为运行时版面，再进入原有编排逻辑。

## 命令分流优先级

当前分流顺序固定如下：

1. 原子命令优先
2. 版面意图识别
3. 兜底任务分类

这样可以保证插入、删除、移动、替换等原子能力不会被版面草案流程误伤。

### 原子命令示例

- `删除22点的节目`
- `把9点的节目后移1小时`
- `在10点插入看东方`

### 版面草案示例

- `帮我填充全天节目`
- `不参考版面，下午排入电视剧`
- `晚上全部替换成新闻栏目`
- `按这个版面开始编排`

## 版面意图识别

版面意图识别输出结构化结果，而不是直接执行命令。当前识别结果包含：

- `mode`
- `ignoreExistingLayout`
- `targetTimeRange`
- `semanticLabel`
- `programTypeHint`
- `confidence`

其中：

- `layout_prepare` 表示生成新草案
- `layout_refine` 表示调整当前草案
- `layout_commit` 表示确认草案并开始编排
- `clarify` 表示信息不足，需要用户补充

## 草案数据结构

LLM 不直接输出最终运行时版面，而是先产出显式时间版 `LayoutDraftSpec`，再由本地编译器转换为 `LayoutDraft`。

核心约束：

- 每个栏目段都必须有明确的 `startTime` 和 `endTime`
- 时间格式固定为 `HH:mm:ss`
- 草案覆盖范围与时段段落分离存储
- 编译后统一落到现有 `LayoutReference + ColumnDefinition` 体系

## 草案展示

草案展示现在只放在右侧对话信息流中：

- 展示整份草案的覆盖时间
- 展示每一条栏目的时间段
- 展示每一条栏目名称
- 支持在卡片内部滚动浏览整份草案

首屏默认不展示预检结果，不展示候选数，不展示风险标签，避免打断用户先看结构、再做调整。

## 草案微调规则

当前已经支持：

- 某时段替换为新的栏目语义
- 某时段整体改成某类内容
- 删除草案中的某一条栏目段

例如：

- `下午改成新闻`
- `晚上全部替换成新闻栏目`
- `去掉23点的两说`

### 删除型微调

删除型草案微调会先按以下线索定位目标栏目段：

- 时间点
- 时间范围
- 栏目名或语义标签

命中后会直接从草案段列表中移除该栏目段。

## 空档处理

草案阶段允许存在空档。

当前策略是：

- `segment_gap` 只作为警告，不阻断草案生成和微调
- 真正阻断的是非法时间、重叠、缺失字段等结构错误

这样可以避免“当前草案历史上已有空档，导致本次微调完全失败”的问题。

## 与编排器的衔接

点击“开始编排”后：

1. 当前草案被注册到运行时版面注册表
2. 保留现有节目单
3. 只在草案覆盖范围内继续补排

这意味着：

- 草案是编排约束，不是左侧表格预渲染结果
- 草案范围外的节目不会被自动重写

## 已知边界

1. 当前对复合命令的支持仍以“单次一个主要目标”为主。
2. 模糊业务短语仍然依赖 LLM 识别和本地兜底组合。
3. 草案阶段只保证结构可持续调整，不保证每一段都一定能找到合适节目。
4. 全量编排的等待时间仍会受到 LLM 调用次数和超时重试策略影响。
