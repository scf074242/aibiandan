# 迭代路线图

更新时间：2026-04-02

## 文档目的

这份路线图不是长期产品规划，而是基于当前仓库现实情况整理出的“下一步怎么做最划算”。

它的目标是：

- 先稳住原型可维护性
- 再补足最重要的功能缺口
- 最后再决定是否走向更真实的产品化方案

## 路线图原则

### 原则 1

先补工程可维护性，再继续堆新功能。

### 原则 2

优先做“能明显降低后续成本”的工作，而不是只做看起来显眼的页面功能。

### 原则 3

如果一个能力还完全依赖 mock，就先把边界写清楚，再决定是否投入产品化开发。

## 阶段划分

### Phase A：文档与基线收口

目标：

- 让团队对“当前做到哪一步”达成统一认知
- 建立最基本的工程质量基线

建议工作项：

1. 完成 README、现状、架构、技术债、功能对齐、路线图文档
2. 清理最明显的 lint 问题
3. 建立最小测试基线
4. 记录本地开发和构建注意事项

完成标志：

- 文档体系可用于 onboarding
- 至少核心服务具备基础测试入口
- lint 错误明显下降，项目不再继续失控

### Phase B：主流程减重与稳定化

目标：

- 在不破坏当前演示能力的前提下，降低改动成本

建议工作项：

1. 拆分 [create.vue](./src/views/broadcast-plan/create.vue)
2. 拆分 [ChatPanel.vue](./src/components/dialogue/ChatPanel.vue)
3. 收口 [orchestrator.ts](./src/services/orchestrator.ts) 的职责
4. 去掉主流程相关文件中的 `@ts-nocheck`
5. 补关键服务测试

完成标志：

- 大文件得到明显缩减
- 主流程逻辑边界更清楚
- 重构不再完全依赖手工回归

### Phase C：补核心缺口面板

目标：

- 把当前“部分实现”的能力补成更完整的演示闭环

建议工作项：

1. 补独立的编排进度面板
2. 补独立的校验报告面板
3. 补版面参考展示或对比面板
4. 明确编辑后自动校验的触发与反馈路径
5. 统一错误、确认、重试的交互体验

完成标志：

- 需求核心主轴中的面板型能力基本齐备
- 演示时不再需要大量口头解释“这里其实有，但没完全做出来”

### Phase D：补数据闭环与低优先级功能

目标：

- 决定这个项目是继续做“高保真前端原型”，还是开始进入半产品态

建议工作项：

1. 评估并实现导出能力
2. 评估并实现历史快照能力
3. 决定是否补节目库生成脚本与真实种子数据
4. 明确数据层替换方案
5. 评估 LLM 调用是否迁出浏览器端

完成标志：

- F08、F09 有明确去留
- mock 与真实数据边界不再含混
- LLM 安全边界有清晰结论

## 推荐优先级排序

如果只能按最务实的顺序推进，建议这样排：

1. 降 lint 负债
2. 建最小测试基线
3. 拆 `create.vue`
4. 拆 `ChatPanel.vue`
5. 收口 `orchestrator.ts`
6. 补校验报告面板
7. 补编排进度面板
8. 补版面参考展示
9. 再决定导出、历史、真实数据接入

## 风险提示

### 风险 1

如果不先做质量基线，后续每补一个功能，维护成本都会继续上升。

### 风险 2

如果过早接真实接口，当前页面层和流程层耦合问题会被进一步放大。

### 风险 3

如果直接上导出、历史等低优先级功能，容易让主流程的技术债继续累积。

## 不建议的推进方式

不建议这样做：

1. 一边继续堆新功能，一边放着 lint 和大文件不管
2. 在没有测试基线的情况下大规模重构目录
3. 在没有收口数据服务层前直接把页面改成真实接口驱动

## 推荐的近期里程碑

### M1

“项目可被新人读懂”

完成条件：

- 文档体系齐全
- 当前状态清楚
- 核心文件职责基本可解释

### M2

“项目主流程可被稳定修改”

完成条件：

- 大文件拆分完成第一轮
- lint 负债明显下降
- 核心服务已有基础测试

### M3

“项目演示闭环更完整”

完成条件：

- 进度面板、校验报告、版面对比能力补齐到可演示程度

### M4

“项目可以决定是否产品化”

完成条件：

- 导出、历史、真实数据、LLM 安全边界都有明确决策

## 一句话结论

当前最合理的路线不是“继续横向加功能”，而是“先把主流程周围的工程地基打平，再往需求文档靠齐”，这样后面的每一步都更便宜、更稳。
